Data source - Container installation notes

This lab assumes you completed lab 2 on the container path, so you already have the perses container running and serving on localhost:8080, and you are sitting in the perses-install-demo directory you unzipped there.

You are going to add Prometheus and the node exporter as two more containers, published to localhost:9090 and localhost:9100 so your browser can query them. If you installed Perses from source instead, this path still works, the two are completely independent of each other.

Container - Starting Podman machine

You need to make sure that the Podman virtual machine is running, so, assuming you have initialized a Podman machine already: 
							
								$ podman machine start
If you want to use other container tooling, such as Docker, most of the commands below are the same with just a substitution of the tooling name (docker instead of podman).

Prometheus install - The configuration

Before we can run our Prometheus instance, we need to explore the lab setup in the provided configuration shown below: 
							
								$ cat support/workshop-prometheus.yml

								# workshop config
								global:
								  scrape_interval: 5s

								scrape_configs:

								  # Scraping prometheus.
								  - job_name: "prometheus"
									static_configs:
									  - targets: ["localhost:9090"]

								  # Scraping node exporter.
								  - job_name: "node"
									static_configs:
									  - targets: ["localhost:9100"]

Prometheus install - Some thoughts on config

Normally you are monitoring other targets over HTTP and scraping their endpoints, but we are going to start with Prometheus as it also exposes its own metrics endpoints and an instance of the Node Exporter. Monitoring these are only an exercise for this workshop. Also note that scraping metrics every 5 seconds is a bit over the top, commonly you would see 10-60 seconds, but we want our data to flow in a steady stream for this workshop.

Container - Creating a pod for both containers

Both containers are going into a single Podman pod, and the ports are published on the pod rather than on the individual containers: 
							
								$ podman pod create --name workshop-datasource \
								    -p 127.0.0.1:9090:9090 \
								    -p 127.0.0.1:9100:9100

								f3c1d9a6e2b74c05a1d8e6f4b39c7a20d5e81fb63c94a7d2e0b58c1f6a3d9e47
Note there is nothing to publish for port 8080 here, your Perses container from lab 2 keeps that one and is not part of this pod.

Intermezzo - Why a pod and not two containers?

Containers in a pod share one network namespace, which means they see each other on localhost exactly as two processes on your laptop would.

That is the whole reason for the pod. The configuration file you just looked at scrapes localhost:9090 and localhost:9100, so it works unchanged in here, and Prometheus writes those same addresses into the instance label. Your variable drop-downs and every screenshot in the rest of this workshop read identically to the local binary path.

Run the two as separate containers on a shared network instead, and you would be scraping node-exporter:9100, which lands a service name in the instance label and leaves you translating labels for the rest of the day.

Prometheus install - Start your metrics engines!

Now start Prometheus inside the pod, mounting our workshop configuration over the one the image ships. Run this from the perses-install-demo directory: 
							
								$ podman run -d --pod workshop-datasource --name prometheus \
								    -v "$(pwd)/support/workshop-prometheus.yml:/etc/prometheus/prometheus.yml:ro,Z" \
								    docker.io/prom/prometheus:v3.13.1
The image already looks for its configuration at /etc/prometheus/prometheus.yml, so there is no flag to pass. The ro,Z mounts it read-only and relabels it for SELinux, harmless on machines without SELinux. On Windows, replace $(pwd) with the full path to the directory.

Prometheus install - Checking the container logs

The container was started detached (-d), so to watch it come up, or to debug a configuration that will not load, ask for the logs: 
							
								$ podman logs -f prometheus

								...
								level=INFO source=main.go:896 msg="Starting Prometheus Server" mode=server version="(version=3.13.1)"
								level=INFO source=web.go:727 msg="Start listening for connections" address=0.0.0.0:9090
								level=INFO source=main.go:1480 msg="TSDB started"
								level=INFO source=main.go:1441 msg="Server is ready to receive web requests."
								...
A container that exited instead of starting is almost always a configuration problem, and the last few log lines will name the file and line for you.

Prometheus install - Verifying instance

Now let's see if our Prometheus server is up and running by loading the status page in our browser at http://localhost:9090, noting it needs to run a little bit to collect some data from its own HTTP metrics endpoint. Click on the menu items STATUS -> TARGET HEALTH to verify it is collecting Prometheus metrics and not yet connecting to the Node Exporter instance (as not yet started):

Node exporter install - Start your node engines!

Now it's time to start the node exporter for Prometheus to start scraping. There is no configuration file needed, and it goes into the same pod: 
							
								$ podman run -d --pod workshop-datasource --name node-exporter \
								    quay.io/prometheus/node-exporter:v1.12.1
It listens on port 9100 by default, which is the port you already published on the pod, so Prometheus starts scraping it on its next 5-second interval with no configuration change.

Intermezzo - Whose machine is being measured?

Worth being honest about what you just started. A node exporter in a container reports on the machine it can see, and from inside a container that is the container's own view of the kernel it is running on. On Mac and Windows, where Podman runs a Linux virtual machine, those numbers describe the virtual machine and not your laptop.

For this workshop that makes no difference, we want a steady stream of real metrics to build panels against, and this gives us exactly that. Just do not read the disk and memory figures as a report on your own hardware. If that is what you are after, the local binaries path measures your machine directly.

Container - Verifying the deployment

You should now have the Perses container from lab 2 running on its own, plus a pod holding Prometheus and the node exporter: 
							
								$ podman ps --pod

								NAMES          STATUS   PORTS                     POD NAME
								perses         Up 21m   127.0.0.1:8080->8080/tcp
								prometheus     Up 4m    127.0.0.1:9090->9090/tcp  workshop-datasource
								node-exporter  Up 47s   127.0.0.1:9100->9100/tcp  workshop-datasource
The pod also runs a small infra container of its own that holds the shared network namespace open, add -a to the command above if you want to see it.

Node exporter install - Verifying instance

Now let's see if our Prometheus server picked up our node instance in our browser at http://localhost:9090, and clicking on the menu items STATUS -> TARGET HEALTH to verify it is collecting Prometheus and Node Exporter metrics (look for the green UP state on the right side):

Verifying - The labels you should see

This is the check that matters for the rest of the workshop. Query up in the expression browser and confirm you get exactly these two series: 
							
								up{instance="localhost:9090", job="prometheus"}  1
								up{instance="localhost:9100", job="node"}        1
If either instance shows a container or service name instead, the containers are not sharing a network namespace. Check that both were started with --pod workshop-datasource.

Container - Cleaning up later on

Not yet, but when you are completely finished with the workshop, removing the pod takes both containers with it. Your Perses container is separate, so stop that one too, and then the virtual machine: 
							
								$ podman pod rm -f workshop-datasource

								$ podman container stop perses

								$ podman machine stop

Data source installed - Results

Prometheus is scraping itself and the node exporter, both are reachable from your browser, and the labels read the same as every other path in this workshop.

Leave the pod running for the rest of the workshop, it is what your dashboards are going to be querying.
