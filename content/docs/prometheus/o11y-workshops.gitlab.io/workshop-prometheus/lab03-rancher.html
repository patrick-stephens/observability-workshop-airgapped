Services demo - Building an image the cluster can see

Kubernetes pulls images from a registry, and we never push this one anywhere. The trick is to build it straight into the image store your cluster reads from. Rancher Desktop ships two container engines, so first check which one you are running under Preferences > Container Engine, then use the matching command: 
							
								# Container engine set to dockerd (moby) - k3s reads the docker image store directly.
								#
								$ docker build --load -t prometheus_services_demo:v1 -f installs/demo/Buildfile installs/demo

								# Container engine set to containerd - build into the k8s namespace.
								#
								$ nerdctl --namespace k8s.io build -t prometheus_services_demo:v1 -f installs/demo/Buildfile installs/demo
Three things bite here. That trailing installs/demo is the build context, and it is not a typo for ., the Go sources and go.mod live in that subdirectory and the build fails without it. On containerd the --namespace k8s.io is not optional, k3s only looks in that namespace, so a plain nerdctl build hides the image from your pod, and it sits in ErrImagePull forever. And on dockerd, if your Docker CLI defaults to a docker-container buildx builder, a plain docker build only leaves the result in the BuildKit cache, never in docker images, hence the --load.

Services demo - Verifying the built image

Looking up our built image to verify everything went well. Ask for it by name, a bare docker images lists every image on your machine and the one we care about is lost in the noise: 
							
								$ docker images prometheus_services_demo

								IMAGE                         ID             DISK USAGE   CONTENT SIZE
								prometheus_services_demo:v1   d039d73640e2       31.8MB         10.1MB
On a containerd set up the command is nerdctl --namespace k8s.io images prometheus_services_demo.

Services demo - A Kubernetes deployment

Using any editor you like, create a file named services-demo.yaml and cut-and-paste the following deployment into it (be sure to save the results): 
							
								apiVersion: apps/v1
								kind: Deployment
								metadata:
								  name: services-demo
								spec:
								  replicas: 1
								  selector:
								    matchLabels:
								      app: services-demo
								  template:
								    metadata:
								      labels:
								        app: services-demo
								    spec:
								      containers:
								      - name: services-demo
								        image: prometheus_services_demo:v1
								        imagePullPolicy: IfNotPresent
								        ports:
								        - containerPort: 8080
Do not skip the imagePullPolicy. The default is Always, which sends Kubernetes off to a registry looking for an image that only exists on your machine.

Services demo - Adding a service

A pod on its own has no stable name to scrape, so add a service to the bottom of the same services-demo.yaml file: 
							
								---
								apiVersion: v1
								kind: Service
								metadata:
								  name: services-demo
								spec:
								  selector:
								    app: services-demo
								  ports:
								  - port: 8080
								    targetPort: 8080
Now apply the whole thing: 
							
								$ kubectl apply -f services-demo.yaml -n prometheus

								deployment.apps/services-demo created
								service/services-demo created

Services demo - Prometheus configuration updates

There is no container IP address to hunt down here, in-cluster DNS does that work for us. Open the workshop-values.yaml file from lab 2 and add a job to the existing scrapeConfigs block: 
							
								# Scraping only Prometheus.
								scrapeConfigs:
								  ...                                        <<<< LEAVE WHAT IS ALREADY THERE

								  # Scraping services demo.
								  services:                                  <<<< ADD THESE FIVE LINES
								    job_name: services
								    static_configs:
								      - targets:
								        - services-demo:8080
Add it inside the block you already have, two spaces in, below whatever is there (the switched-off Kubernetes jobs, plus the prometheus job if you fixed the broken target exercise back in lab 2). A second scrapeConfigs: key further down the file silently wins and throws away everything above it.

Services demo - Applying the configuration

No image to rebuild and no signal to send, you re-run the exact same helm upgrade --install command from lab 2 and the configmap-reload sidecar tells Prometheus to reload itself: 
							
								$ helm upgrade --install workshop-prometheus prometheus-community/prometheus \
								    --version 29.20.0 \
								    --namespace prometheus --create-namespace \
								    -f workshop-values.yaml

								Release "workshop-prometheus" has been upgraded. Happy Helming!
								NAME: workshop-prometheus
								NAMESPACE: prometheus
								STATUS: deployed
								REVISION: 3
This is the Kubernetes answer to the kill -s HUP of the source path and to the rebuild-and-restart of the container path. Same lesson, three very different mechanics.

Services demo - Configuration applied

Validate the new configuration was picked up by checking the log output, you should see something like this: 
							
								$ kubectl logs -n prometheus deploy/workshop-prometheus-server -c prometheus-server

								...
								time=2026-08-03T13:41:16.902Z level=INFO source=main.go:1678 msg="Loading configuration file" filename=/etc/config/prometheus.yml
								time=2026-08-03T13:41:16.903Z level=INFO source=main.go:1717 msg="Completed loading of configuration file" db_storage=4.708µs remote_storage=2.916µs web_handler=584ns query_engine=1.875µs scrape=128.75µs scrape_sd=21.416µs notify=1.833µs notify_sd=1.375µs rules=182.417µs tracing=4.125µs filename=/etc/config/prometheus.yml totalDuration=873.25µs
								...
Be patient, this is not instant. Helm updates the ConfigMap the moment the command returns, but Kubernetes copies it into the running pod on its own schedule, and only then does configmap-reload notice and trigger the reload. Up to a minute between a successful helm upgrade and Prometheus actually using your change is normal.

Until that happens, the console keeps serving the old configuration, so a target you just fixed can still be sitting there red with the error it had before you edited anything. Do not start changing things again. Wait for the two lines above to appear in the log, that is the moment the new configuration is live, and only then judge the targets page.

Services demo - Opening the Prometheus console

Time to look at the results in the Prometheus console, but there is nothing listening on your machine yet. The server only has a ClusterIP service, reachable from inside the cluster, so the port-forward from lab 2 is what puts it on localhost:9090. If you still have that terminal window open, skip ahead. If you closed it, or it dropped while you were deploying, start it again: 
							
								$ kubectl port-forward -n prometheus svc/workshop-prometheus-server 9090:9090

								Forwarding from 127.0.0.1:9090 -> 9090
								Forwarding from [::1]:9090 -> 9090
Now load http://localhost:9090 in your browser. Before querying, use the STATUS drop-down and pick TARGETS, you should see the services job listed and UP alongside the prometheus one. An empty graph on the next slide almost always means this page is showing the target as down.

Do not click the target links. That page shows each target's scrape URL written from Prometheus's point of view, from inside the cluster, so http://services-demo:8080/metrics is a name only the cluster can resolve and your browser lands on nothing. That is not a broken target, the UP next to it is Prometheus telling you it fetched that endpoint just fine. To read those metrics yourself, use your port-forwards on localhost:8080 instead.

You are up to three terminal windows now, one port-forward each for Prometheus and the services demo, plus the one you type in. That is normal for this path, closing any of the forwards just cuts that connection, nothing in the cluster is harmed.
