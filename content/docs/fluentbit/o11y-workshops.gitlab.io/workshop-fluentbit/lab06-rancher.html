Data loss - Same OOM, different mechanism

Just as in the backpressure lab, the OOM kill on Kubernetes is not a container-runtime feature, it is the Linux kernel cgroup memory limit and its OOM killer. On the Podman path we set that limit with --memory. On Kubernetes we set it with resources.limits.memory on the pod's container.

We again assume you deployed Fluent Bit onto k3s with Rancher Desktop back in labs 3 - 5, so it is already running from the Helm values file workshop-fb-helm.yaml. If not, make sure you have Rancher Desktop running before continuing. We'll first reproduce the data loss (OOMKilled) pipeline, then fix it with filesystem buffering.

Data loss - Configuration inputs (k3s)

We begin with the INPUT phase, a simple dummy plugin generating a large amount of entries to flood our pipeline (note the previous mem_buf_limit fix is commented out). Update the extraFiles block in workshop-fb-helm.yaml, keeping the http_server lines so the liveness probe on port 2020 keeps passing: 
							
								args:
								  - --workdir=/fluent-bit/etc
								  - --config=/fluent-bit/etc/conf/fluent-bit.yaml

								config:
								  extraFiles:
								    fluent-bit.yaml: |
								      service:
								        flush: 1
								        log_level: info
								        http_server: on
								        http_listen: 0.0.0.0
								        http_port: 2020

								      pipeline:
								        inputs:
								          # This entry generates a large amount of success messages for the workshop.
								          - name:  dummy
								            tag:   big.data
								            copies: 15000
								            dummy: '{"message":"true 200 success", "big_data": "blah blah blah blah blah blah blah blah"}'

Data loss - Configuring outputs (k3s)

Continuing in the same file, add the outputs section below the inputs, directing all tags to the pod's console (stdout): 
							
								      pipeline:
								        inputs:
								          ...

								        outputs:
								          # This entry directs all tags to the console (pod stdout).
								          - name: stdout
								            match: '*'
								            format: json_lines

Data loss - Constraining the pod memory

To cause the OOM we constrict the pod's memory. Add a resources block to the same workshop-fb-helm.yaml values file, giving the container a tight limit (here around 13Mi, adjust on your machine until you see it run a bit of logging before being killed): 
							
								resources:
								  limits:
								    memory: 13Mi
								  requests:
								    memory: 13Mi

Data loss - Rolling out stressed pipeline (k3s)

Apply the updated configuration with a helm upgrade from the fluentbit-install-demo root directory. This rolls out a new Fluent Bit pod with our flooding pipeline and the tight memory limit: 
							
								$ helm --kube-context rancher-desktop upgrade --install fluent-bit fluent/fluent-bit \
								       --set image.tag=5.1.1 \
								       --namespace logging --create-namespace \
								       --values workshop-fb-helm.yaml

								Release "fluent-bit" has been upgraded. Happy Helming!
								NAME: fluent-bit
								NAMESPACE: logging
								STATUS: deployed
								REVISION: 7

Data loss - Watching the pod fail (k3s)

Watch the pod in the logging namespace. It runs for a moment, floods memory, and Kubernetes kills it. Unlike the one-shot Podman container, a Helm-managed pod restarts, so you will see it cycle into OOMKilled and then CrashLoopBackOff: 
							
								$ kubectl --context rancher-desktop -n logging get pods -w

								log-generator-cf9d79d46-xgvc9   1/1     Running           1          3m

								fluent-bit-6c8f9                0/1     CrashLoopBackOff  1         20s

Data loss - Validating stressed == OOM (k3s)

To validate our data loss scenario worked, describe the pod and inspect the last container state. The following shows that the kernel killed our container due to an OOM error, reported as OOMKilled with exit code 137: 
							
								$ kubectl --context rancher-desktop -n logging describe pod -l app.kubernetes.io/name=fluent-bit

								...

								  Finished:     ...

Data loss - Confirming the OOM (k3s)

You can also confirm the OOM kill in a scriptable way by reading the terminated container's last state directly from the pod status, which reliably reports OOMKilled: 
							
								$ kubectl --context rancher-desktop -n logging get pod \
										-l app.kubernetes.io/name=fluent-bit \
										-o jsonpath='{.items[0].status.containerStatuses[0].lastState.terminated.reason}'

								OOMKilled

Data loss - Prevention with filesystem buffering

What we've seen is that when a channel floods with too many events to process, our pipeline pod fails. From that point onwards we are now unable to collect, process, or deliver any more events.

Already having tried in a previous lab to manage this with mem_buf_limit settings, we've seen that this also is not the real fix. To prevent data loss, we need to enable filesystem buffering so that overloading the memory buffer means that events will be buffered in the filesystem until there is memory free to process them. Let's try this...

Data loss - Filesystem buffering (k3s)

The INPUT phase needs a slight adjustment by adding storage.type: filesystem as shown, along with a few SERVICE section attributes to enable it, all inside the same extraFiles block: 
							
								config:
								  extraFiles:
								    fluent-bit.yaml: |
								      service:
								        flush: 1
								        log_level: info
								        http_server: on
								        http_listen: 0.0.0.0
								        http_port: 2020
								        storage.path: /tmp/fluentbit-storage
								        storage.sync: normal
								        storage.checksum: off
								        storage.max_chunks_up: 5

								      pipeline:
								        inputs:
								          # This entry generates a large amount of success messages for the workshop.
								          - name:  dummy
								            tag:   big.data
								            copies: 15000
								            dummy: '{"message":"true 200 success", "big_data": "blah blah blah blah blah blah blah blah"}'
								            storage.type: filesystem

Data loss - Notes about SERVICE section

The properties that might need some explanation are:

  • storage.path – putting filesystem buffering in the tmp filesystem
  • storage.sync – using normal and turning off checksum processing
  • storage.max_chunks_up – set to ~10MB, amount of allowed memory for events

Data loss - Rolling out filesystem pipeline (k3s)

With filesystem buffering in place the pod survives, spilling events to disk instead of overrunning memory. Adjust to give it a touch more headroom in workshop-fb-helm.yaml than before (for me around 15Mi, tune on your machine) and roll it out again: 
							
								$ helm --kube-context rancher-desktop upgrade --install fluent-bit fluent/fluent-bit \
								       --set image.tag=5.1.1 \
								       --namespace logging --create-namespace \
								       --values workshop-fb-helm.yaml

Data loss - Console output filesystem pipeline (k3s)

First confirm the pod is actually surviving (RESTARTS should stay at 0), then follow its logs in the logging namespace. The pipeline now runs without failing, with events rolling by steadily as the filesystem absorbs the overflow (exit with CTRL-C): 
							
								$ kubectl --context rancher-desktop -n logging logs -l app.kubernetes.io/name=fluent-bit -f

								...
								{"date":1753280450.742,"message":"true 200 success","big_data":"blah blah blah blah blah blah blah blah"}
								{"date":1753280450.742,"message":"true 200 success","big_data":"blah blah blah blah blah blah blah blah"}
								{"date":1753280450.743,"message":"true 200 success","big_data":"blah blah blah blah blah blah blah blah"}
								...

Data loss - Validating filesystem buffering (k3s)

The Fluent Bit image is distroless (no shell, no ls), so instead of poking at the buffer files we ask Fluent Bit itself. Its HTTP server on port 2020 is already enabled, and the Kubernetes API server can proxy an HTTP GET straight to the fluent-bit service — no port-forward needed. Query /api/v1/storage and pipe to your local jq; a non-zero fs_chunks count proves filesystem buffering: 
							
								# Ask the API server to proxy an HTTP GET to the fluent-bit service on port 2020.
								$ kubectl --context rancher-desktop -n logging get --raw \
										'/api/v1/namespaces/logging/services/fluent-bit:2020/proxy/api/v1/storage' \
										| jq '.storage_layer.chunks'

								{
								  "total_chunks": 42,
								  "mem_chunks": 5,
								  "fs_chunks": 37,
								  "fs_chunks_up": 5,
								  "fs_chunks_down": 32
								}

Data loss - Thoughts on filesystem solution

This solution is the way to deal with backpressure and other issues that might flood your telemetry pipeline and causing it to crash. It's worth noting that using a filesystem to buffer the events also introduces the limits of the filesystem being used.

It's important to understand that just as memory can run out, so too can the filesystem storage reach its limits. It's best to have a plan to address any possible filesystem challenges when using this solution, but this is outside the scope of this workshop.
