Routing - Understanding routing in telemetry pipelines

Routing is a core feature that lets you route your data through filters and then to one or multiple destinations. In production environments, you rarely send all your telemetry data to a single destination. Different types of logs need different handling:

  • Error logs - might go to an alerting system
  • Audit logs - to long-term storage
  • Debug logs - might be dropped entirely to save costs


Fluent Bit provides multiple routing mechanisms to handle these scenarios, and understanding these routing patterns is essential for developers who want to build sophisticated telemetry pipelines that efficiently direct data where it needs to go.

Routing - Three routing mechanisms

Fluent Bit provides three primary routing mechanisms:

  • Tag-based routing - The traditional approach that uses tags and matching rules to determine where data flows. This method routes entire chunks of data based on their assigned tags.
  • Conditional routing - A newer approach (Fluent Bit 4.2+) that uses conditions to evaluate individual records and route them to different outputs based on their content. This provides fine-grained, per-record routing decisions.
  • Label-based matching - A mechanism used with direct routing that stores labels and plugin names in chunk metadata to enable stable routing even when output configuration changes.

Routing - Where routing happens in a pipeline

Routing happens throughout the pipeline but is most evident in the final output phase, where we decide which processed events go to which destinations:

Tag-based routing - The traditional approach

Tag-based routing is the traditional routing mechanism in Fluent Bit. It relies on two key concepts:

  • Tag - A human-readable identifier assigned to data at the input stage
  • Match - A pattern rule configured on outputs to select which tagged data to receive


When data is generated by an input plugin, it comes with a Tag. The tag is usually configured manually in the input configuration. To define where to route data, specify a Match rule in the output configuration.

If data has a Tag that doesn't match any output at routing time, the data is deleted!

Tag-based routing - Basic tag matching

Let's start with a basic tag matching example. Create a new directory workshop-routing and a configuration file routing-fb.yaml with the following configuration: 
							
								# Basic tag-based routing configuration.
								#
								service:
								  flush: 1
								  log_level: info
								  http_server: on
								  http_listen: 0.0.0.0
								  http_port: 2020
								  hot_reload: on

								pipeline:
								  inputs:
								    - name: dummy
								      tag: app.frontend
								      dummy: '{"service":"frontend","message":"User request received"}'

								    - name: dummy
								      tag: app.backend
								      dummy: '{"service":"backend","message":"Processing database query"}'

								  outputs:
								    # Only matches frontend events.
								    - name: stdout
								      match: app.frontend
								      format: json_lines

Tag-based routing - Using wildcards

Wildcards let you match multiple tags with a single pattern. Update your configuration to route both frontend and backend events: 
							
								outputs:
								  # Match all events starting with 'app.'
								  - name: stdout
								    match: 'app.*'
								    format: json_lines

								  # Route frontend to a dedicated file.
								  - name: file
								    match: 'app.frontend'
								    file: /tmp/frontend.log

								  # Route backend to a different file.
								  - name: file
								    match: 'app.backend'
								    file: /tmp/backend.log
The pattern app.* matches any tag starting with app. followed by any characters at one level.

Tag-based routing - Understanding wildcard levels

It's important to understand how wildcards work with tag hierarchies:

  • Single asterisk (*) - Matches any characters at one level only
    • app.* matches app.frontend and app.backend
    • app.* does NOT match app.frontend.logs
  • Double asterisk (**) - Matches multiple levels of the hierarchy
    • app.** matches app.frontend, app.backend, AND app.frontend.logs


Tags typically follow a hierarchical naming convention like app.frontend.logs or system.metrics.cpu. This structure makes it easy to create wildcard patterns for flexible matching.

Tag-based routing - Using regular expressions

For more complex matching, use match_regex with regular expressions. Update the configuration to demonstrate regex matching: 
							
								pipeline:
								  inputs:
								    - name: dummy
								      tag: sensor_A.temperature
								      dummy: '{"sensor":"A","type":"temperature","value":22.5}'

								    - name: dummy
								      tag: sensor_B.humidity
								      dummy: '{"sensor":"B","type":"humidity","value":65}'

								  outputs:
								    # Regex: Match any tag containing 'sensor_' followed by A or B.
								    - name: stdout
								      match_regex: 'sensor_[AB]\..*'
								      format: json_lines
The regex sensor_[AB]\..* matches any tag starting with sensor_A. or sensor_B. followed by anything.

Conditional routing - Per-record routing decisions

Conditional routing is a powerful feature introduced in Fluent Bit 4.2 that lets you route individual records to different outputs based on their content. Unlike tag-based routing which operates on entire data chunks, conditional routing evaluates conditions against each record.

Key advantages of conditional routing:

  • Per-record decisions - Route based on individual record content
  • No tag modification needed - Route without filters changing tags
  • Explicit configuration - Routing logic is clear and maintainable
  • Early evaluation - Decisions made at input stage before filtering


Note: Conditional routing requires YAML configuration files.

Conditional routing - Configuration syntax

Conditional routing uses a routes block within input configurations. Here's the basic structure: 
							
								pipeline:
								  inputs:
								    - name: input_plugin_name
								      tag: input_tag
								      routes:
								        logs:
								          - name: route_name
								            condition:
								              op: {and|or}
								              rules:
								                - field: {field_name}
								                  op: {comparison_operator}
								                  value: {comparison_value}
								            to:
								              outputs:
								                - output_alias_or_name

								  outputs:
								    - name: output_plugin_name
								      alias: output_alias

Conditional routing - Comparison operators

The following comparison operators are available for condition rules:

OperatorDescription
eqEqual to
neqNot equal to
gtGreater than
ltLess than
gteGreater than or equal to
lteLess than or equal to
regexMatches a regular expression
not_regexDoesn't match a regular expression
inIs included in the specified array
not_inIsn't included in the specified array

Conditional routing - Route by severity level

Let's create a practical example that routes logs by severity level. Create a new configuration file conditional-routing.yaml and adding a route for error logs: 
							
								service:
								  flush: 1
								  log_level: info

								pipeline:
								  inputs:
								    - name: dummy
								      tag: app.logs
								      dummy: '{"level":"error","message":"Database connection failed"}'
								      routes:
								        logs:
								          - name: error_logs
								            condition:
								              op: or
								              rules:
								                - field: "$level"
								                  op: eq
								                  value: "error"
								                - field: "$level"
								                  op: eq
								                  value: "fatal"
								            to:
								              outputs:
								                - error_output
								                - all_logs_output

Conditional routing - Adding more routes

Continue the configuration by adding routes for info logs and a default catch-all route: 
							
								          # Continuing from previous routes block...
								          - name: info_logs
								            condition:
								              op: and
								              rules:
								                - field: "$level"
								                  op: eq
								                  value: "info"
								            to:
								              outputs:
								                - info_output
								                - all_logs_output

								          - name: default_logs
								            condition:
								              default: true
								            to:
								              outputs:
								                - all_logs_output

								    # Add a second input to generate info messages.
								    - name: dummy
								      tag: app.logs
								      dummy: '{"level":"info","message":"Application started successfully"}'
								      routes:
								        logs:
								          - name: info_route
								            condition:
								              default: true
								            to:
								              outputs:
								                - info_output
								                - all_logs_output

Conditional routing - Configuring outputs with aliases

Now add the output configurations with aliases that match the routes. Note that outputs use alias to be referenced by conditional routes: 
							
								  outputs:
								    # Error logs go to dedicated file.
								    - name: file
								      alias: error_output
								      match: '*'
								      file: /tmp/errors.log

								    # Info logs go to a separate file.
								    - name: file
								      alias: info_output
								      match: '*'
								      file: /tmp/info.log

								    # All logs also go to stdout for visibility.
								    - name: stdout
								      alias: all_logs_output
								      match: '*'
								      format: json_lines

Conditional routing - Using the 'in' operator

The in operator is useful for matching against multiple values. Here's an example routing critical services to a dedicated output, passing the message only if it has a serivce key with the value matching any in the list of payment, authentication, database: 
							
								pipeline:
								  inputs:
								    - name: dummy
								      tag: services.logs
								      dummy: '{"service":"payment","message":"Transaction processed"}'
								      routes:
								        logs:
								          - name: critical_services
								            condition:
								              op: and
								              rules:
								                - field: "$service"
								                  op: in
								                  value: ["payment", "authentication", "database"]
								            to:
								              outputs:
								                - critical_output

								          - name: standard_services
								            condition:
								              default: true
								            to:
								              outputs:
								                - standard_output

Conditional routing - Multiple conditions with 'and'

Combine multiple conditions for precise routing. This example routes high-priority production errors to multiple destinations if all the highlighted rules are met: 
							
								routes:
								  logs:
								    - name: high_priority_errors
								      condition:
								        op: and
								        rules:
								          - field: "$level"
								            op: eq
								            value: "error"
								          - field: "$environment"
								            op: eq
								            value: "production"
								          - field: "$response_time"
								            op: gt
								            value: 5000
								      to:
								        outputs:
								          - alerting_output
								          - archive_output

								    - name: all_logs
								      condition:
								        default: true
								      to:
								        outputs:
								          - archive_output

Conditional routing - Using regex matching

Use regular expressions for flexible content matching. This example routes security-related events based on message content, highlighting the regex matching rules: 
							
								routes:
								  logs:
								    - name: security_events
								      condition:
								        op: or
								        rules:
								          - field: "$message"
								            op: regex
								            value: "(?i)(unauthorized|forbidden|authentication failed)"
								          - field: "$event_type"
								            op: regex
								            value: "^security\\."
								      to:
								        outputs:
								          - security_output

								    - name: other_logs
								      condition:
								        default: true
								      to:
								        outputs:
								          - general_output
The (?i) flag makes the regex case-insensitive.

Label-based matching - Stable routing across changes

Label-based matching is a feature that enhances direct routing by storing labels and plugin names in chunk metadata. This enables stable routing that survives configuration changes, restarts, and output reordering.

When chunks are created with direct routes, Fluent Bit stores routing information in chunk metadata including:

  • Labels - User-provided aliases or automatically generated names like stdout.0, file.1
  • Plugin names - The plugin type to enable type-safe matching


Label-based matching is automatically used when direct routing is enabled and is available in Fluent Bit 4.2 and greater.

Label-based matching - Benefits

Label-based matching provides several advantages:

  • Configuration resilience - Chunks continue routing to the correct outputs even when output IDs change due to configuration reordering
  • Stable routing after restarts - When Fluent Bit restarts and loads chunks from storage, it can restore routes using labels instead of relying solely on numeric IDs
  • Type safety - Plugin name matching prevents routing to outputs of different plugin types
  • Backward compatibility - Chunks without labels fall back to numeric ID matching


To leverage label-based matching effectively, assign meaningful aliases to your outputs!

Label-based matching - Best practices

Here's an example showing how to use aliases effectively for stable routing with an example collecting logs from a Kubernetes pod: 
							
								pipeline:
								  inputs:
								    - name: tail
								      path: /var/log/app/*.log
								      tag: app.logs
								      routes:
								        logs:
								          - name: production_logs
								            condition:
								              op: and
								              rules:
								                - field: "$environment"
								                  op: eq
								                  value: "production"
								            to:
								              outputs:
								                - prod_logs_output    # Reference by alias

								  outputs:
								    - name: elasticsearch
								      alias: prod_logs_output     # Stable identifier
								      host: prod-logs.example.com
								      index: production-logs

Label-based matching - Recommendations

To get the most benefit from label-based matching, follow these best practices:

  • Use aliases - Assign meaningful aliases to your outputs to make routing more stable and easier to understand
  • Keep aliases unique - Ensure that aliases are unique within your configuration to avoid ambiguity
  • Use descriptive names - Choose aliases that clearly indicate the purpose of each output:
    • error_logs_output
    • audit_logs_destination
    • debug_logs_archive
  • Combine with direct routing - Label-based matching works best when used with direct routing (conditional routing or direct input-output connections)

Advanced routing - Choosing a routing approach

Use these guidelines to choose between routing approaches:

Use CaseRecommended Approach
Route all data from an input to specific outputsTag-based routing
Route data based on source or input typeTag-based routing
Route individual records based on contentConditional routing
Split logs by severity or other field valuesConditional routing
Apply different processing to subsets of dataConditional routing
Routing without content inspectionTag-based routing
Stable routing that survives config changesLabel-based matching
Routing after restarts with storage backlogLabel-based matching


You can combine multiple approaches in a single configuration for maximum flexibility!

Advanced routing - Why is an info event in errors.log?

Look closely at errors.log above, and you'll spot an info level backend event sitting in a file we meant for errors. That is not a mistake, it's the two routing mechanisms both feeding the same output. The prefix on each line tells you which one delivered it:
  • frontend_errors: is a route name, so that record arrived by conditional routing from the frontend input
  • app.backend: is a tag, so that record arrived by tag-based matching
Our error_file output is declared with match: '*', which matches every tag we generate. The backend input has no routes block, so it falls back to tag-based routing, and '*' happily catches it. Meanwhile, the frontend input does have routes, so its records skip tag matching entirely, which is why they never appear in the all_logs console stream despite it matching 'app.*'.

Narrow the match to fix it, for example match: 'app.frontend', and errors.log then holds only the conditionally routed errors. This is the trade-off worth remembering when combining approaches, as an alias does not make an output private to a route.

Routing - Summary of key concepts

You now have a solid understanding of Fluent Bit routing:

  • Tag-based routing - Traditional approach using tags and match patterns with wildcards (*) and regular expressions (match_regex)
  • Conditional routing - Per-record routing based on content (Fluent Bit 4.2+) using conditions with operators like eq, in, regex, and more
  • Label-based matching - Stable routing using output aliases that survives configuration changes and restarts
  • Combined approaches - Use tag-based for broad categorization and conditional for fine-grained decisions


These routing patterns are essential for building production-ready telemetry pipelines that efficiently direct data where it needs to go while minimizing costs!
