Data source - Kubernetes installation notes

This lab assumes you completed lab 2 on the Kubernetes path, so you already have a local cluster running with Perses installed in the perses namespace and a port-forward serving it on localhost:8080.

You are going to add Prometheus and the node exporter to that same namespace using the community Helm chart, and forward Prometheus to localhost:9090 so your browser can query it. If you have not done lab 2 on this path yet, go back and do that first.

Setup - Adding the Helm repository

Add the Prometheus community chart repository and confirm the chart version you are about to install ships the Prometheus version this workshop is built on:

Setup - A workshop values file

Create a file called workshop-values.yaml with the following contents: 
							
								# workshop config
								server:
								  image:
								    tag: v3.13.1
								  global:
								    scrape_interval: 5s
								    scrape_timeout: 4s
								  persistentVolume:
								    enabled: false
								  service:
								    servicePort: 9090

								# Keep the workshop lean - but we DO want the node exporter.
								alertmanager:
								  enabled: false
								kube-state-metrics:
								  enabled: false
								prometheus-pushgateway:
								  enabled: false
								prometheus-node-exporter:
								  enabled: true
								  fullnameOverride: node-exporter
								  image:
								    tag: v1.12.1
Note the scrape_timeout must be smaller than the scrape_interval, the chart writes both out and Prometheus refuses to start if the timeout is the larger of the two. The fullnameOverride is there because the subchart would otherwise name the service workshop-perses-prometheus-prometheus-node-exporter.

Setup - Trimming down the chart

The chart also ships a set of Kubernetes scrape jobs we don't need, and we want one job of our own for the node exporter. Add this block at the very bottom of the same workshop-values.yaml file: 
							
								# Scraping Prometheus and the node exporter only.
								scrapeConfigs:
								  node:                                        <<<< ADD THESE SIX LINES
								    job_name: node
								    static_configs:
								      - targets: ["node-exporter:9100"]
								        labels:
								          instance: "localhost:9100"
								  kubernetes-api-servers: { enabled: false }
								  kubernetes-nodes: { enabled: false }
								  kubernetes-nodes-cadvisor: { enabled: false }
								  kubernetes-service-endpoints: { enabled: false }
								  kubernetes-service-endpoints-slow: { enabled: false }
								  kubernetes-services: { enabled: false }
								  kubernetes-pods: { enabled: false }
								  kubernetes-pods-slow: { enabled: false }
								  prometheus-pushgateway: { enabled: false }
Watch the indentation. Everything under scrapeConfigs is indented two spaces, and the rest of the file sits at the left margin. Do not add a second scrapeConfigs: line, YAML quietly lets the last one win.

Intermezzo - Why pin the instance label?

That instance: "localhost:9100" line is doing something worth understanding. Left alone, Prometheus sets the instance label to whatever address it scraped, which in a cluster is a service DNS name, not localhost:9100.

Setting the label explicitly on the target tells Prometheus not to fill it in for you. That keeps the variable drop-downs and the example dashboards in the rest of this workshop reading exactly the same on this path as they do on the local binary path, so you can follow along without mentally translating every screenshot.

This is ordinary Prometheus relabeling, not a trick. It is also a good reminder that labels are something you control, not something handed down to you.

Installation - Deploying the Helm chart

Install Prometheus into the same perses namespace, from the directory holding your values file: 
							
								$ helm upgrade --install workshop-perses-prometheus prometheus-community/prometheus \
								    --version 29.20.0 \
								    --namespace perses \
								    -f workshop-values.yaml

								Release "workshop-perses-prometheus" does not exist. Installing it now.

								workshop-perses                     ClusterIP  10.43.74.55    8080/TCP

								node-exporter                       ClusterIP  10.43.175.34   9100/TCP

Intermezzo - That 2/2 is not a typo

The Prometheus pod reports 2/2 because the chart runs a configmap-reload sidecar alongside the server. It watches the ConfigMap holding your scrape configuration and tells Prometheus to reload when it changes.

That is why there is no workshop-prometheus.yml to edit on this path. Your configuration lives in workshop-values.yaml, Helm renders it into the ConfigMap, and to apply a change you re-run the same helm upgrade --install command. Give it up to a minute, ConfigMap updates do not propagate instantly.

Installation - Start your metrics engines!

Prometheus is a ClusterIP service too, so forward it to your machine on the same localhost:9090 the rest of this workshop expects. Leave this running in its own console window, alongside the Perses port-forward from lab 2: 
							
								$ kubectl port-forward -n perses svc/workshop-perses-prometheus-server 9090:9090

								Forwarding from 127.0.0.1:9090 -> 9090
								Forwarding from [::1]:9090 -> 9090
You now need two port-forwards running: 8080 for Perses and 9090 for Prometheus.

Installation - Checking the server logs

If you want to watch Prometheus start up, or debug a configuration that will not load, the logs are one command away (use a third console window): 
							
								$ kubectl logs -n perses -f \
								    deploy/workshop-perses-prometheus-server -c prometheus-server
The -c prometheus-server matters, without it kubectl has to guess which of the two containers in that pod you meant.

Verifying - Checking your targets

Open the Prometheus status page in your browser at http://localhost:9090, and look under Status > Target health. Both jobs should be UP:

Verifying - The labels you should see

This is the check that matters for the rest of the workshop. Query up in the expression browser and confirm you get exactly these two series: 
							
								up{instance="localhost:9090", job="prometheus"}  1
								up{instance="localhost:9100", job="node"}        1
If the node instance shows a service name or a pod IP instead, your instance label did not take. Recheck the indentation of the labels: block in your values file and re-run the helm upgrade.

Kubernetes - Cleaning up later on

Not yet, but when you are completely finished with the workshop, stopping your port-forwards and deleting the namespace removes both Helm releases, Perses, Prometheus, the node exporter, and everything else these labs created: 
							
								$ kubectl delete namespace perses

Data source installed - Results

Prometheus is scraping itself and the node exporter, both are reachable from your browser, and the labels read the same as every other path in this workshop.

Leave both port-forwards running for the rest of the workshop, 8080 for Perses and 9090 for Prometheus, they are what your dashboards are going to be querying.
