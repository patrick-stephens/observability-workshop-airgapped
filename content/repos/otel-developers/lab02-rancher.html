Auto-instrument - Rancher k3s prerequisites

This path runs the demo application on a local Rancher Desktop k3s cluster instead of straight on your machine. You still need Podman v5+ to build the images and Java 21 with Maven 3.8+ to build the JAR that goes into them, plus Rancher Desktop with the Kubernetes (k3s) engine enabled and kubectl on your PATH.
You never download the Java Agent by hand on this path - each build file pulls it in with ADD, so it lands inside the image.

Auto-instrument - Getting started

The OpenTelemetry Java Agent provides automatic instrumentation by attaching to the JVM and dynamically injecting bytecode. This means you get tracing without changing a single line of your application code. The agent automatically instruments:

  • HTTP clients and servers
  • Database calls
  • Messaging systems
  • And many more libraries

Auto-instrument - Demo project introduction

The Java Tracing Demo project is a simple Java HTTP server designed to demonstrate OpenTelemetry instrumentation. It includes endpoints for page views, random dog images, and dice rolls.

Auto-instrument - Java Agent in container

The first option is to auto-instrument in a container by adding the agent JAR and include -javaagent:/app/opentelemetry-javaagent-2.30.0.jar in the ENTRYPOINT. Create a file called Buildfile-AgentContainer with the following content: 
							
								FROM eclipse-temurin:21
								WORKDIR /app

								# Download the OpenTelemetry Java Agent
								ADD https://github.com/open-telemetry/opentelemetry-java-instrumentation/\
								releases/download/v2.30.0/opentelemetry-javaagent.jar /app/opentelemetry-javaagent-2.30.0.jar

								COPY target/java-instrumentation-demo-1.0-SNAPSHOT-with-dependencies.jar /app/app.jar

								ENTRYPOINT ["java", "-javaagent:/app/opentelemetry-javaagent-2.30.0.jar", "-jar", "/app/app.jar"]
								EXPOSE 9999
In the next slide we will build and run this container to verify the auto-instrumentation.

Auto-instrument - Understanding the configuration

The agent takes the same settings whether they arrive as -D system properties or as environment variables. In Kubernetes you always use the environment form:

  • -javaagent:/app/opentelemetry-javaagent-2.30.0.jar - baked into the image's ENTRYPOINT, so the pod spec never mentions it
  • OTEL_SERVICE_NAME=java-demo - sets the service name for traces
  • OTEL_TRACES_EXPORTER=logging - exports traces to the container log, which is what kubectl logs shows you
  • OTEL_METRICS_EXPORTER=none - disables metrics for now
  • OTEL_LOGS_EXPORTER=none - disables log export for now
The host path also passes -Xshare:off to silence a class-data-sharing warning. The images here do not set it, so you may see that warning in the pod log - it is harmless.

Auto-instrument - Using JAVA_TOOL_OPTIONS

An alternative is using JAVA_TOOL_OPTIONS where the JVM automatically picks up this environment variable. Create a file called Buildfile-AgentJavaTools with the following content: 
							
								FROM eclipse-temurin:21
								WORKDIR /app

								ADD https://github.com/open-telemetry/opentelemetry-java-instrumentation/\
								releases/download/v2.30.0/opentelemetry-javaagent.jar /app/opentelemetry-javaagent-2.30.0.jar

								COPY target/java-instrumentation-demo-1.0-SNAPSHOT-with-dependencies.jar /app/app.jar

								# Agent attaches automatically via JAVA_TOOL_OPTIONS
								ENV JAVA_TOOL_OPTIONS="-javaagent:/app/opentelemetry-javaagent-2.30.0.jar"

								ENV OTEL_TRACES_EXPORTER=logging
								ENV OTEL_METRICS_EXPORTER=none
								ENV OTEL_LOGS_EXPORTER=none

								ENTRYPOINT ["java", "-jar", "/app/app.jar"]
								EXPOSE 9999
In the next slide we will build and run this container to verify the auto-instrumentation with this approach.

Intermezzo - JAVA_TOOL_OPTIONS benefits

Benefits of the JAVA_TOOL_OPTIONS approach:

  • No need to modify the java command or ENTRYPOINT
  • Works with any existing Java container image
  • Configuration baked in but can be overridden at runtime
  • Easy to disable: --env="JAVA_TOOL_OPTIONS="
Try that last one - every baked-in setting can be overridden from the pod spec: 
							
								$ kubectl run java-demo-noagent --image=localhost/java-demo:java-tools \
								  --image-pull-policy=Never --port=9999 --env="JAVA_TOOL_OPTIONS="

								$ kubectl logs -f pod/java-demo-noagent
The log has no [otel.javaagent] lines and no spans - the agent never attached. Clean up with kubectl delete pod java-demo-noagent.

Intermezzo - Overriding to OTLP

The override you would actually use in production swaps the console exporter for OTLP. On a cluster two things have to be right, and the second one catches people out:
  • Something has to be listening for OTLP - we have no collector in the cluster yet, that arrives in the next lab with Jaeger
  • The agent defaults to http://localhost:4318, which inside a pod is that pod's loopback. It only works if the collector is a second container in the same pod - otherwise point it at a Service, or at the host
							
								$ kubectl run java-demo-otlp --image=localhost/java-demo:java-tools \
								  --image-pull-policy=Never --port=9999 \
								  --env="OTEL_TRACES_EXPORTER=otlp" \
								  --env="OTEL_EXPORTER_OTLP_ENDPOINT=http://jaeger:4318"
Don't run this yet - with nothing listening the agent logs Failed to export spans every few seconds. Lab 6 shows the shared-pod pattern.

Intermezzo - Why mounting the agent does not translate

The Podman path shows a third pattern: keep the agent out of the image entirely and mount it at runtime with -v ./opentelemetry-javaagent-2.30.0.jar:/otel/agent.jar:ro. That one does not carry over to k3s.

The pod runs inside the Rancher Desktop VM, so a path on your laptop is not a path the kubelet can see. A hostPath volume would resolve inside the VM, not on your host, and whether your home directory happens to be mounted there depends on the Rancher Desktop version and VM backend - not something a workshop should rely on.

In Kubernetes the agent normally arrives one of two ways: baked into the image, as in the two patterns you just ran, or copied in by an init container sharing an emptyDir volume. The operator does the latter for you.

Read the mounted-agent slides on the Podman path for the pattern itself.

Stop the port-forward with CTRL-C, then remove every pod this lab created so host port 9999 is free for the next one: 
							
								$ kubectl delete pod java-demo-base       --ignore-not-found
								$ kubectl delete pod java-demo-auto       --ignore-not-found
								$ kubectl delete pod java-demo-java-tools --ignore-not-found
								$ kubectl delete pod java-demo-noagent    --ignore-not-found

								$ kubectl get pods
								No resources found in default namespace.
Two pods cannot claim the same host port on a single node, so any left from one lab will make the next one fail to start.
