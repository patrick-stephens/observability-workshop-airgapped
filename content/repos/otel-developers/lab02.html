Auto-instrument - Getting started

The OpenTelemetry Java Agent provides automatic instrumentation by attaching to the JVM and dynamically injecting bytecode. This means you get tracing without changing a single line of your application code. The agent automatically instruments:

  • HTTP clients and servers
  • Database calls
  • Messaging systems
  • And many more libraries

Auto-instrument - Download the Java Agent

Download the OpenTelemetry Java Agent JAR file (v2.30.0): 
							
								$ curl -L -o opentelemetry-javaagent-2.30.0.jar \
									https://github.com/open-telemetry/opentelemetry-java-instrumentation/releases/download/v2.30.0/opentelemetry-javaagent.jar
This downloads version of the agent (~20MB) matching the SDK v1.65+ requirement.

Auto-instrument - Run with the Java Agent

Run the application with the Java Agent attached and configure it to export traces to the console: 
							
								$ java -javaagent:opentelemetry-javaagent-2.30.0.jar \
								-Xshare:off \
								-Dotel.service.name=java-demo \
								-Dotel.traces.exporter=logging \
								-Dotel.metrics.exporter=none \
								-Dotel.logs.exporter=none \
								-jar target/java-instrumentation-demo-1.0-SNAPSHOT-with-dependencies.jar

Auto-instrument - Understanding the flags

The flags used in the previous command could use some explanation:

  • -javaagent:opentelemetry-javaagent-2.30.0.jar - attaches the OTel agent to the JVM
  • -Xshare:off - disables class data sharing (CDS) to avoid conflicts with agent bytecode instrumentation
  • -Dotel.service.name=java-demo - sets the service name for traces
  • -Dotel.traces.exporter=logging - exports traces to console/logs
  • -Dotel.metrics.exporter=none - disables metrics for now
  • -Dotel.logs.exporter=none - disables log export for now

Auto-instrument - Java Agent in container

The first option is to auto-instrument in a container by adding the agent JAR and include -javaagent:/app/opentelemetry-javaagent-2.30.0.jar in the ENTRYPOINT. Create a file called Buildfile-AgentContainer with the following content:

								ENTRYPOINT ["java", "-javaagent:/app/opentelemetry-javaagent-2.30.0.jar", "-jar", "/app/app.jar"]
								EXPOSE 9999

Auto-instrument - Using JAVA_TOOL_OPTIONS

An alternative is using JAVA_TOOL_OPTIONS where the JVM automatically picks up this environment variable. Create a file called Buildfile-AgentJavaTools with the following content: 
							
								FROM eclipse-temurin:21
								WORKDIR /app

								ADD https://github.com/open-telemetry/opentelemetry-java-instrumentation/\
								releases/download/v2.30.0/opentelemetry-javaagent.jar /app/opentelemetry-javaagent-2.30.0.jar

								COPY target/java-instrumentation-demo-1.0-SNAPSHOT-with-dependencies.jar /app/app.jar

								# Agent attaches automatically via JAVA_TOOL_OPTIONS
								ENV JAVA_TOOL_OPTIONS="-javaagent:/app/opentelemetry-javaagent-2.30.0.jar"
								ENV OTEL_SERVICE_NAME=java-demo
								ENV OTEL_TRACES_EXPORTER=logging
								ENV OTEL_METRICS_EXPORTER=none
								ENV OTEL_LOGS_EXPORTER=none

								ENTRYPOINT ["java", "-jar", "/app/app.jar"]
								EXPOSE 9999
In the next slide we will build and run this container to verify the auto-instrumentation with this approach.

Auto-instrument - Build and verify JAVA_TOOL_OPTIONS

Build the image and run - no extra flags needed! 
							
								$ podman build -t java-demo:java-tools -f Buildfile-AgentJavaTools

								$ podman run --rm --name java-tools-container -p 9999:9999 java-demo:java-tools
Everything is baked into the image - agent attachment and OTel configuration. No runtime flags needed, making deployment simple and consistent.

Intermezzo - JAVA_TOOL_OPTIONS benefits

Benefits of the JAVA_TOOL_OPTIONS approach:

  • No need to modify the java command or ENTRYPOINT
  • Works with any existing Java container image
  • Configuration baked in but can be overridden at runtime
  • Easy to disable: -e JAVA_TOOL_OPTIONS=""
Try that last one - every baked-in setting can be overridden from the outside: 
							
								$ podman run --rm -p 9999:9999 -e JAVA_TOOL_OPTIONS="" java-demo:java-tools
Make a request and notice the console has no [otel.javaagent] lines and no spans at all - the agent never attached. Stop it with CTRL-C.

Intermezzo - Overriding to OTLP

The override you would actually use in production swaps the console exporter for OTLP. Two things have to be right, and the second one catches people out:
  • Something has to be listening for OTLP - we have no collector running yet, that arrives in the next lab with Jaeger
  • Inside a container, localhost is the container, not your machine. The agent defaults to http://localhost:4318, so it must be pointed at the host explicitly
							
								$ podman run --rm -p 9999:9999 \
									-e OTEL_TRACES_EXPORTER=otlp \
									-e OTEL_EXPORTER_OTLP_ENDPOINT=http://host.containers.internal:4318 \
									java-demo:java-tools
Don't run this yet - with nothing listening on 4318 the agent logs Failed to export spans ... Connection refused every few seconds and no traces appear anywhere. Come back to it once Jaeger is up in lab 3.
